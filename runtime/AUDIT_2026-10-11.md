## Umfang und Belege

Anbindung, Start-/Endereignisse, ActionLedger, Neustarts, Kontextübergaben,
Fehler-/Stop-Sicherung, Lock und Zyklusschleife. Dazu Startprompt, Ausführungsvertrag,
Runtime-Anleitung und alle vorhandenen Python-Tests. Das ist kein vollständiges
Sicherheits- oder Gameplay-Audit sämtlicher HTML-/JS-Spiele.

Die vom Nutzer gezeigten lokalen Belege enthalten:

- abgeschlossener code_interpreter_docker-Aufruf, success=false, etwa 7,75 Sekunden;
- FileNotFoundError für `/home/pagi/breachline-agent/repo/quickpuzzle/index.html`;
- fehlenden Host-Ordner quickpuzzle, vorhandenen Host-Checkout mit Benutzer-Schreibrecht;
- FAILED/potential_write=true im Receipt und im Manifest
  `Uncertain side effects ... No automatic replay.`;
- keinen Treffer für den Scheduler-Prozess.

Die Bilder belegen einen einzelnen fehlgeschlagenen Aufruf. Sie allein belegen
nicht alle möglichen Teilwirkungen des ausgeführten Codes. Deshalb benötigt die
gezielte Freigabe zusätzlich einen überprüften isolierten Ausführungspfad.

## Begrenzte Wiederaufnahme

Für den gezeigten Fehler wird der bereits gespeicherte letzte Run geprüft, bevor
ein neuer Run angelegt wird. Nur ein vollständig erhaltener, abgeschlossener
FileNotFoundError-Traceback von code_interpreter_docker wird zugelassen, wenn die
installierte Implementierung und Standard-Factory dem unten geprüften Code
entsprechen. Der Prüfstatus lautet FAILED_ISOLATED: kein Host-Mount, kein erfolgreicher
Spielbau. Die ursprünglichen FAILED-Receipts bleiben unverändert.

Die Prüfung speichert Resultatdigest, Quelldigests, Receipt-Digest und Aktionen.
Der nächste Agent erhält den Prüfverweis sowie den Auftrag, tatsächliche Host-Dateien
zu prüfen und einen korrigierten Host-Schritt zu wählen. Kein automatischer Replay
des alten Python-Skripts. Die Werkzeugauswahl verhindert den gleichen Container-
Pfadfehler im normalen nächsten Zyklus.

PENDING, Timeout, fehlendes/ungepaartes Resultat, Resultat außerhalb des Runs,
unbekannte/angepasste Toolimplementierung und weitere unklare Host-/Social-Aktionen
bleiben gesperrt. Eine Lock-Datei wird nicht gelöscht; flock entscheidet über einen
laufenden Prozess. Sicherheitsrichtlinien und 0-Euro-/Freigabenvertrag bleiben aktiv.

## Primärquellen und Quellprüfung

Offizieller OpenJarvis-Code, während dieses Audits direkt gelesen:

- [Docker-Codeinterpreter](https://github.com/open-jarvis/OpenJarvis/blob/main/src/openjarvis/tools/code_interpreter_docker.py): read_only=True, temporäres /tmp, standardmäßig network_disabled=True, keine volumes/mounts, Entfernung des Containers.
- [CLI / _build_tools](https://github.com/open-jarvis/OpenJarvis/blob/main/src/openjarvis/cli/ask.py): Standardinstanziierung tool_cls() für den Docker-Codeinterpreter.
- [Docker-Shell](https://github.com/open-jarvis/OpenJarvis/blob/main/src/openjarvis/tools/docker_shell_exec.py): aktiver TerminalBench-Container erforderlich; ausdrücklich keine Host-Shell-Alternative.
- [file_write](https://github.com/open-jarvis/OpenJarvis/blob/main/src/openjarvis/tools/file_write.py): create_dirs=false als Standard; true erstellt Elternverzeichnisse.
- [shell_exec](https://github.com/open-jarvis/OpenJarvis/blob/main/src/openjarvis/tools/shell_exec.py): Host-Ausführung mit optionalem working_dir und bestehender Sicherheitsprüfung.

Der Wiederaufnahme-Guard nutzt normalisierte Python-AST-Digests (Positionsdaten
ausgeschlossen); Kommentare/Formatierung verändern den Digest nicht, funktionale
Änderungen und Docstring-Änderungen schon. Es wird keine Docker-Ausführung gestartet.

## Validierung und Grenzen

- `python3 -m unittest discover -s tests`: **52 Tests erfolgreich**, davon 42 Scheduler-/Integrationstests und 10 Instagram-Adaptertests.
- Regression: Screenshot-Traceback + alte FAILED-Receipts werden nach geprüfter Isolation freigegeben, Originaldateien bytegleich erhalten; wiederholte Prüfung bleibt möglich.
- Negative Prüfungen: fehlende Quellenprüfung, abweichende Factory/Registry, fehlendes/externes Resultat, unpaarige Ereignisse, Timeout, PENDING und zusätzlich fehlgeschlagene Shell bleiben gesperrt.
- Agentintegration: ungemeldeter zweiter file_write-Fehler wird trotz früherem Erfolg erkannt; Resultate und Fehlerhistorie sind gespeichert.
- Vorhandene Kontextfortsetzung, Modell-Retry ohne Tool-Replay, Loader-/Regelgrenzen und Instagram-Duplikat-/Tokenprüfungen bleiben erfolgreich.
- Zusätzlicher Smoke-Test mit dem tatsächlich gelesenen offiziellen Docker-/Factory-Quelltext und isolierten Import-Doubles: produktiver Quellguard akzeptiert beide Digests, Default-Netzwerkflag ist true. Kein Container und keine Remote-Schreibaktion ausgeführt.
- `python3 -m compileall -q runtime tests` und `git diff --check`: erfolgreich.

Der Ubuntu-Rechner, dessen installierte OpenJarvis-Version, Ollama und tatsächliche
Dateien sind hier nicht direkt erreichbar. Der erste echte Start nach git pull
ist deshalb noch eine lokale Runtime-Abnahme. Bei abweichendem installiertem Code
bleibt die Quelle konkret zu prüfen; der Guard behauptet dann keine sichere Isolation.
Keine Aussage über einen fertigen QuickPuzzle-Prototyp oder erfolgreiche Pages-
Veröffentlichung. Die bisherigen Fehlerversuche werden nicht als Produktfortschritt
umgedeutet.

## Übernahme

Im bestehenden gestoppten Setup:

```bash
git -C /home/pagi/breachline-agent/repo pull --ff-only origin agent-lab
cd /home/pagi/breachline-agent
~/.openjarvis/.venv/bin/python -u repo/runtime/jarvis_loop.py
```

Kein Reset, keine neue config.toml, keine erneut kopierten Briefing-/Logvorlagen.
Beim gezeigten Fehler ist RECOVERY ISOLATED_FAILURE_REVIEW der erwartete Prüfhinweis.
Wenn der bisher benutzte OpenJarvis-Interpreter an einem anderen Pfad liegt, diesen
vorhandenen Interpreter verwenden. Rückweg: vorherige Scheduler-Version als gezielte
Codeänderung wiederherstellen; keine Laufprotokolle löschen und keine pauschalen
Working-Tree-Resets ausführen.
